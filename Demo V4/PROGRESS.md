# V4 진행 현황과 다음 검증 계획

2026년 11월 24일 · Team Connecting

## 현재 구현 범위

TCP 파일 전송이 중단되면 Python이 장애를 감지하고 재접속해 저장된 위치부터 이어받습니다. Solar는 복구 직전에 `resume` 또는 `restart`를 제안하고, Python이 적용 조건을 확인해 실행합니다. 전송 후에는 관측 로그와 선택적으로 수집한 패킷 요약을 이용해 장애 유형과 근거를 진단합니다. 완료된 파일은 크기와 SHA-256으로 원본과 대조합니다.

| 단계 | 주요 구현 및 확인 내용 |
|---|---|
| 초기 데모 | 중단 감지, 자동 재접속, 오프셋 기반 이어받기, 최종 SHA-256 검증. 같은 조건의 처음부터 받기와 비교해 재접속 후 전송량 절감 확인 |
| V2 | 재접속 거절과 응답 헤더 중간 종료 이후의 재시도. 패킷 캡처 저장 및 Wireshark에서 연결 종료·새 연결 시도 확인 |
| V3 | 정상, 조기 연결 종료, 수신 시간 초과, 증거 부족 사례 구성. 규칙 기반 진단과 실제 Solar를 비교하는 결과표 추가 |
| V4 | 복구 전략 제안, 실제 API 요청·응답과 적용 결과 기록, 반복 진단 평가. 중단 관측과 최종 전송 결과를 각각 응답하도록 진단 형식 개선 |

## 실제 Solar 연동 결과

실제 모델은 `solar-pro4-260806`이며 요청 시 별칭 `solar-pro4`를 사용했습니다. 첫 실제 연동에서 복구 전략 적용과 파일 검증이 성공했습니다. 사후 진단에서는 중단이 있었음에도 완료·해시 검증 이벤트만 인용해 정상으로 오판하는 현상이 나타났습니다. 같은 입력과 지침으로도 조기 종료 판정이 달라져, 응답 형식에 관측 중단과 최종 결과를 명시적으로 추가했습니다.

- `interruption_evidence_ids`에 관측된 중단 이벤트를 기록합니다.
- `transfer_outcome`과 `outcome_evidence_ids`에 공개 로그에서 확인한 최종 전송·해시 검증 결과를 기록합니다.
- `diagnosis`와 `evidence_ids`에는 전체 관측 구간의 장애 판정과 근거를 기록합니다.

중단 이후 복구에 성공한 실행은 중단 이벤트와 `verified_complete`를 함께 반환할 수 있습니다. 기존 진단 정답·근거 지지 평가는 유지했고, 새 필드에 대한 관측 평가를 추가했습니다. 모델의 원래 응답과 각 평가 결과를 보관했습니다.

### 동일 자료 반복 평가

네 가지 사례의 동일한 관측 자료를 변경 전후 각각 3회 진단했습니다. 각 단계는 새로운 전송 실험 12회가 아니라, 네 관측 자료에 대한 실제 API 요청 12회입니다.

| 조건 | 변경 전 진단·근거 통과 | 변경 후 진단·근거 통과 | 변경 후 중단·완료 구분 |
|---|---:|---:|---:|
| 정상 | 3/3 | 3/3 | 3/3 |
| 조기 연결 종료 | 2/3 | 3/3 | 3/3 |
| 수신 시간 초과 | 3/3 | 3/3 | 3/3 |
| 증거 부족 | 3/3 | 3/3 | 3/3 |
| 합계 | 11/12 | 12/12 | 12/12 |

이번 자료의 재평가에서는 변경 후 조기 종료 오판이 관찰되지 않았습니다. 모델의 일반적인 진단 정확도와 반복 안정성을 판단하려면 다양한 새 입력과 추가 반복이 필요합니다.

### 새 관측 자료 검증

네 조건을 새로 실행한 뒤 개선한 형식으로 실제 Solar를 호출했습니다. 진단, 인용 근거, 중단·완료 구분 모두 4/4 통과했고 최종 파일 크기와 해시도 4/4 일치했습니다. 복구가 필요한 세 조건에서 실제 Solar의 `resume` 제안을 적용했습니다. 정상 조건은 전략 요청이 필요하지 않았습니다. 증거 부족 조건은 내부 전송을 복구한 뒤 사후 진단용 자료만 일부 공개했습니다.

이 실제 API 실험에서는 패킷 캡처를 요청하지 않았습니다. 진단에 사용한 자료는 애플리케이션 관측 로그입니다.

## 데이터 무결성 기준 보완

현재는 임시 파일 길이와 수신 기록을 비교해 이어받기 위치를 정하고, 전송 완료 후 전체 SHA-256을 비교합니다. 길이가 일치해도 저장된 바이트 내용이 변경됐을 수 있으므로, 이어받기 전의 부분 데이터 검증을 다음 구현 대상으로 정합니다.

| 검사 | 판단 기준 | 현재 상태 |
|---|---|---|
| 저장 위치 | `.part` 크기와 수신 기록의 바이트 수 일치 | 구현됨 |
| 서버 파일 버전 | 재접속 시 서버의 전체 크기와 SHA-256 식별값을 기존 값과 대조 | 구현됨 |
| 저장 부분의 내용 | `.part` SHA-256과 서버 원본의 같은 길이 구간 SHA-256 일치 | 추가 구현 필요 |
| 최종 파일 | 전체 크기와 SHA-256이 원본과 일치 | 구현됨 |

부분 검증에서는 서버 파일 식별값과 요청 오프셋을 함께 확인합니다. 클라이언트의 저장 부분과 서버 원본의 처음 N바이트가 일치하면 N부터 이어받고, 다르면 처음부터 다시 받도록 합니다. 해시 계산과 비교는 Python이 수행하고 Solar에는 그 확인 결과를 전달합니다. 최종 전체 파일 검증은 계속 수행합니다.

완료 기준은 정상 부분 파일의 이어받기 성공, 길이는 유지한 채 내용을 변경한 부분 파일의 불일치 감지, 파일 버전 변경 감지, 복구 후 최종 해시 일치입니다. 현재 Solar의 설명 중 저장 길이 일치를 데이터 내용의 완전성으로 표현한 문장은 수정 대상입니다. 현재 근거에 맞는 설명은 저장 길이가 기록과 일치해 이어받기를 시도하며 최종 무결성을 SHA-256으로 검증한다는 것입니다.

## 수신 시간 초과의 원인 진단 보완

`recv timeout`은 설정한 대기 시간 안에 데이터를 받지 못했다는 관측입니다. 현재 `stall` 실험은 서버가 송신을 의도적으로 지연시켜 이 상황을 재현합니다. Solar가 전략 설명에서 일시적 네트워크 문제로 추정한 부분은 관측 자료가 지지하는 범위를 넘어섭니다. 자동 전략·진단 평가와 함께 설명의 각 주장이 증거를 갖추었는지 사람이 검토해야 합니다.

| 확인할 원인 후보 | 추가 관측 | 통제 실험 방향 |
|---|---|---|
| 서버 송신 지연 | 서버의 송신 예정·실제 시각, 서버 측 패킷 송신 시각 | 서버 대기 시간을 조절해 클라이언트 수신 기록과 대조 |
| 패킷 지연·손실 | 양쪽 캡처, TCP 스트림과 시퀀스 범위, 재전송, 실험의 드롭 카운터 | 격리 환경에서 지연·손실을 주입하고 실제 주입 기록과 진단 대조 |
| 수신 프로그램 처리 지연 | 클라이언트 측 패킷 도착 시각, 수신 함수 실행·저장 시각, 처리 시간 | 프로그램 처리를 지연시켜 패킷 도착과 앱 처리 사이의 차이 관측 |

TCP 재전송 표시는 같은 연결의 재전송을 분석하는 근거이며, 손실 위치나 원인을 단정하려면 추가 증거가 필요합니다. 양쪽 캡처를 대조할 때에는 시계 기준과 캡처 위치도 기록합니다. 원인을 구분할 증거가 부족하면 Solar는 관측한 증상, 가능한 원인, 추가로 필요한 증거를 명시하도록 개선합니다.

## 다음 진행 순서

1. 복구 전략 설명에 저장 위치 확인과 데이터 내용 검증을 구분해 적도록 지침을 보완합니다. 수신 시간 초과의 원인 추정에는 근거와 불확실성을 요구합니다.
2. 부분 SHA-256 검증을 추가하고 같은 길이의 내용 변경과 서버 파일 버전 변경을 테스트합니다.
3. 서버 지연과 패킷 지연·손실 실험을 각각 구성하고 관측 증거와 주입 정답을 대조합니다.
4. 새 조건에서도 실제 Solar를 반복 평가해 진단 정답, 근거 지지, 관측 구분, 전략 적용, 최종 파일 검증, 설명의 타당성을 기록합니다.

진행 기록과 평가 자료는 main에서 공유하고, 부분 데이터 검증과 원인 진단의 구현은 각각 작업 브랜치에서 검토한 뒤 통합합니다.
