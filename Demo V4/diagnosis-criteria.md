# v3 전송 장애 진단 기준

현재 진단기는 파일 전송 애플리케이션에서 관측한 상태를 네 가지로 판정한다. 패킷에서 확인한 TCP 재전송과 최종 파일의 SHA-256 검증 결과를 함께 기록한다.

## 애플리케이션 판정

| 판정 | 필요한 관측 근거 | 기록할 내용 |
|---|---|---|
| 전송 장애 미관측 (`no_failure_observed`) | `TRANSFER_COMPLETED`와 `SHA256_OK`가 있고 `INTERRUPTED`, `ATTEMPT_FAILED`가 없음 | 두 완료 이벤트 ID를 인용한다. 같은 연결에서 TCP 재전송이 관측되면 패킷 관측란에 기록한다. |
| 전송 중 연결 종료 (`early_connection_close`) | 예상 크기를 받기 전에 `INTERRUPTED`가 기록되었고 사유가 `connection closed` 또는 `connection reset`임 | 해당 중단 이벤트를 인용한다. 캡처가 있으면 중단 전후 TCP 스트림과 FIN 또는 RST의 방향을 참고한다. 종료 주체를 판단하려면 송신 측의 종료 로그처럼 방향을 뒷받침하는 증거가 필요하다. |
| 수신 시간 초과 (`timeout_or_stall`) | 예상 크기를 받기 전에 `INTERRUPTED`가 기록되었고 사유가 `recv timeout`임 | 해당 중단 이벤트를 인용한다. 이 로그로 수신 대기 시간 초과를 확인한다. 원인 판단에는 서버 송신 시각과 클라이언트 도착 시각 등 추가 관측이 필요하다. |
| 판단 보류 (`insufficient_evidence`) | 시작만 관측됐거나, 인정 가능한 중단 사유가 없고 완료·해시 검증 기록도 부족하거나, 서로 다른 중단 사유가 함께 관측됨 | `withheld=true`와 필요한 추가 증거를 기록한다. 예를 들어 중단 사유, 수신 완료 또는 해시 검증 이벤트를 요청한다. |

## TCP 재전송과 파일 이어받기

| 관측 | 필요한 증거 | 확인할 수 있는 내용 |
|---|---|---|
| 같은 연결에서 TCP 재전송 | 캡처의 같은 `tcp.stream`에서 데이터 시퀀스 번호가 다시 나타나고 재전송 표시가 있음 | 프로그램에 재접속 기록이 없고 해시가 일치하면 같은 TCP 연결에서 전송을 완료했다. 재전송 수는 캡처 도구의 분류 결과로 기록한다. 실제 손실 수는 통제 실험의 드롭 카운터 같은 독립적인 증거로 확인한다. |
| 새 연결에서 파일 이어받기 | 앱 로그의 `RECONNECTED` 이후 `REQUEST offset > 0` | 중단 시 저장량과 요청 오프셋이 일치하는지 확인한다. 캡처가 있으면 중단 전과 재접속 후의 TCP 스트림이 다름을 확인한다. 최종 파일이 검증된 경우에 이어받기 성공으로 기록한다. |
| 새 연결에서 처음부터 다시 받기 | 앱 로그의 `RECONNECTED` 이후 `REQUEST offset = 0` | 이전 연결에서 저장한 데이터가 있었으면 `RESTART_RESET` 로그로 폐기 여부도 확인한다. 최종 파일이 검증된 경우에 다시 받기 성공으로 기록한다. |

## 기존 실험에 적용한 결과

| 실험 | 규칙 기반 판정 | 실제 근거 |
|---|---|---|
| 정상 전송 | `no_failure_observed` | 완료 `E006`, SHA-256 일치 `E008`. TCP 스트림 1개. |
| 강제 조기 종료 | `early_connection_close` | 중단 `E007`, 재접속 `E008`, `1,398,101`바이트부터 요청 `E009`. TCP 스트림 2개. |
| 수신 시간 초과 | `timeout_or_stall` | 시간 초과 `E008`, 재접속 `E011`, `1,398,101`바이트부터 요청 `E012`. 서버 지연은 실험에서 설정한 조건으로 보관한다. |
| 증거 부족 | `insufficient_evidence` | 전송 시작 `E004`와 송신 시작 `E005`가 보인다. 제공된 증거로는 중단 사유와 최종 해시를 확인할 수 없다. |
| TCP 패킷 한 개 손실 | `no_failure_observed` | 캡처의 11번과 39번 프레임은 같은 `Seq=4500`을 사용한다. 39번 프레임에 빠른 재전송이 표시됐다. 드롭 카운터 1개, TShark 재전송 표시 39건, TCP 스트림 1개, 재요청 없이 SHA-256 일치. |

정상·조기 종료·시간 초과의 근거 ID는 `Sample Evidence` 안의 사례별 `evidence.jsonl`에서 확인할 수 있다. 증거 부족은 반복 실험 `run-20261116T142246664378-04`를 사용했다. 패킷 손실은 `loss_artifacts/run-20261118T150510732960`의 캡처, 요약, 앱 로그를 사용했다. 같은 `E008`이라도 실행별로 다른 이벤트를 가리킨다.

## Solar 비교 기준

1. 기존 네 가지 진단 사례에서 **판정 일치, 인용 ID 존재와 근거의 적절성, 판단 보류, 호출 실패**를 기록한다. 호출 실패는 틀린 진단과 구분한다.
2. 진단 입력에는 관측 로그와 패킷 요약을 제공한다. 실험 조건명과 장애 주입 기록은 정답 확인에 사용한다.
3. 현재 평가기는 규칙 기반 판정에 앱 로그를 사용하고 Solar 요청에 앱 로그와 패킷 요약을 제공한다. 패킷 손실 사례는 별도의 패킷 해석 평가에 활용한다. TCP 재전송을 설명할 수 있는지와, 파일 전송의 장애 여부를 올바르게 판정했는지를 각각 확인한다.
